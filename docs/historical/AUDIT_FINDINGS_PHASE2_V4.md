# نتائج المرحلة الثانية — جرد الكود والخصائص والواجهة v4

## صورة المشروع

يحتوي المشروع حالياً على 94 ملف TSX و36 ملف TS و5 مسارات API و12 لوحة و10 ملفات ألعاب. الجرد أحصى 254 وسم button، و106 استخدامات لمكون Button، و455 معالج onClick، و42 حقل إدخال، و85 setTimeout، و7 setInterval، و16 استدعاء fetch، و65 موضعاً لطلبات التأكيد أو confirm. هذه الأرقام تبرر مصفوفة اختبارات واسعة متعددة الترتيبات، لأن المخاطر الأكبر ليست في الدوال المنفردة فقط بل في تتابع النقر والتنقل والإغلاق والمؤقت.

## ما هو واضح ومتسق

تؤكد وثائق الفلسفة أن التطبيق Host Shell للمدرس، وأن الشريحة معزولة داخل iframe وتتواصل عبر postMessage. المتجر المركزي يفصل حالة الدرس والأسئلة والجلسة والطلاب والبانلز والسبورة والاحتفالات، مع حفظ UI settings والجلسة النشطة في localStorage وحفظ البيانات الأساسية في SQLite عبر API.

مصادر الأسئلة موحدة عبر lessonQuestions وaskedQuestionIds، وهناك حواجز حضور وعدالة ومراجعة سابقة لمنع التكرار ومضاعفة النقاط. كما أن إضافة MathToolsPanel وReportsPanel ومحرك math-engine وتصدير PDF جعلت الترقية الرياضية مرتبطة بالـshell بدلاً من مسار مستقل.

## نقاط خطر مؤكدة تحتاج اختبارات أو إصلاحاً

### 1. مساران للاحتفالات

يوجد المسار الأحدث DB-driven عبر CelebrationsPanel وCelebrationsOverlay، ويوجد EffectsEngine قديم يقرأ confettiSignal وcelebrationType ويحوّل الصوت إلى نوع تأثير وكلمة عربية. كما أن `shell-utils.ts` يحتوي محرك canvas-confetti واسعاً ومربوطاً بمنطقة stage. يجب اختبار هل المساران مركبان معاً في الصفحة عند إطلاق `triggerCelebration` أو `triggerConfetti`، لأن الخطر هو Banner مزدوج، كلمة مزدوجة، صوت مزدوج، أو تأثيرين متراكبين.

### 2. نوع الاحتفال غير مكتمل في العقد الحالي

`CelebrationConfig` يحتوي label/icon/colors/tagline/hype/sound لكنه لا يحتوي renderMode أو preset أو intensity أو target أو reason. لذلك لا يمكن حالياً حفظ اختيار Confetti مقابل Particles من لوحة الإدارة. يلزم توسيع العقد مع migration آمنة وdefaults تحفظ السلوك القديم.

### 3. اختلاف التوثيق عن التنفيذ

التوثيق يذكر 36 احتفالاً افتراضياً، وهذا يتطابق مع `DEFAULT_CELEBRATIONS`، لكنه يصف بعض التحديثات مثل StudentDNA وSmartAudio وLessonIntelligence وStudentViewMode كميزات موجودة دون أن تكون كلها متساوية في عمق التكامل. يجب مطابقة كل ميزة مع مسار UI واختبار قبول، وعدم اعتبار وجود اسم الملف دليلاً على اكتمال السلوك.

### 4. PDF له مساران مختلفان

`src/lib/shell-utils.ts` يستخدم jsPDF ثابتاً لإنشاء نسخ الطالب والمدرس، بينما `src/lib/pdf-export.ts` يستخدم التقاط DOM للشرائح والسبورة والتقارير. يلزم توحيد metadata والأسماء واللغة وفحص كل مسار، لأن نجاح تنزيل ملف DOM لا يثبت سلامة ملف jsPDF العربي، والعكس صحيح.

### 5. مفاتيح الاختصار قد تتصادم

دليل التشغيل يذكر `R` للطالب العشوائي، بينما الشريط الجانبي يذكر `R2` لقلم قوس قزح، و`S` يختار الأشكال التي لها ثلاثة أنواع. يلزم اختبار focus داخل الحقول، ووجود لوحة مفتوحة، ووجود iframe، وحالة OBS، حتى لا ينفذ الاختصار أثناء كتابة المدرس أو يطبق فعلاً مختلفاً عن الظاهر في الـtooltip.

### 6. وضع OBS يحتاج تحققاً مستقلاً

العقد يحدد ما يظهر للطلاب وما يبقى للمدرس، لكن الجرد يحتاج اختبار screenshot/DOM يثبت أن التليبرومبتر والنوتس والبانلز لا تظهر في مسار العرض المقصود، وأن الاحتفال والسبورة داخل حدود `.iframe-visible-area` لا يغطيان عناصر خارجية.

### 7. AI الحالي عام وغير منظم

مسار `/api/ai` يدعم التشفير وتدوير مفاتيح Google والـrate limit وgenerate النصي، وAiPanel يضم أوضاعاً عامة مثل lesson/questions/analysis/activity. لا توجد بعد عقود JSON منظمة للتحليل أو توليد أسئلة مرتبطة بالدرس أو مساعدة سبورة قابلة للمعاينة. الإضافة الآمنة يجب أن تبقى server-side، وتتحقق من المخرجات قبل إدخالها للمنهج أو اللعبة.

### 8. الاحتفالات والتسجيل

`triggerCelebration` يسجل الطالب الموجود في `currentlyCalledStudent` فقط. هذا صحيح للحفاظ على ملكية المدرس، لكنه لا يميز حالياً بين احتفال لطالب ومجموعة وصف، ولا يسجل سبباً تعليمياً أو skillId. يجب إضافة حقول اختيارية دون كسر السجلات القديمة، مع منع تسجيل طالب إذا لم يكن مختاراً صراحة.

## نتيجة المرحلة

تم تثبيت خريطة الكود والواجهة والبانلز والمسارات الأساسية. المرحلة التالية هي بناء خريطة العقود والمخاطر والـinvariants، ثم تدقيق API وقاعدة البيانات ومصدر الأسئلة قبل إجراء تغييرات جديدة، حتى لا تُضاف AI أو Particles أو ألعاب جديدة فوق مسارات متعارضة غير مكتشفة.

     students: Student[],
     ideaId: string,
     liveStatuses: Map<string, StudentLiveStatus>
   ): Student | null {
     // 1. فلتر الطلاب الحاضرين

### المهمة 8: تدوير مفاتيح API متعددة المصادر

### 5.1: نظام أولوية وتدوير مفاتيح API — المواصفة الإلزامية

لا يكفي أن تكون المفاتيح في قائمة واحدة؛ المطلوب بناء **مجدول مفاتيح متعدد المستويات** يجعل المدرس قادراً على إضافة عدد كبير من المفاتيح، وترتيبها، وإيقافها، ومعرفة حالتها، مع انتقال تلقائي وآمن عند فشل المفتاح الحالي. النظام خاص باستدعاءات AI فقط، ولا يخلط مفاتيح AI مع Token الخاص بـMoodle.

#### أ. نموذج المفتاح والحالة

يجب أن يمثل كل مفتاح سجلاً typed لا تُرسل أسراره إلى المتصفح، مثل:

```typescript
type ApiKeyStatus = "active" | "cooldown" | "failed" | "disabled" | "needs-check";
type Provider = "google" | "groq" | "openai" | "mistral";

interface AiApiKeyRecord {
  id: string;
  provider: Provider;
  label: string;
  encryptedSecret: string;       // AES-256-GCM server-side فقط
  priority: number;               // 1 أعلى أولوية؛ الأرقام الأقل تُجرّب أولاً
  enabled: boolean;
  status: ApiKeyStatus;
  cooldownUntil: number | null;
  supportedModels: string[];
  rpmLimit?: number;
  dailyLimit?: number;
  maxConcurrency: number;
  inFlight: number;
  consecutiveFailures: number;
  successCount: number;
  lastUsedAt: number | null;
  lastSuccessAt: number | null;
  lastErrorCode: string | null;
  lastErrorAt: number | null;
  createdAt: number;
  updatedAt: number;
}
```

يُحفظ السر مشفراً في الخادم أو قاعدة البيانات المحلية، ويظهر في الواجهة باسم مقنّع مثل `••••••••9f2a`. لا يُكتب المفتاح أو جزء منه في logs أو telemetry أو رسائل الخطأ أو payloads للعميل. **Token Moodle منفصل كلياً عن مفاتيح AI ولا يدخل في نظام تدوير مفاتيح AI.**

#### ب. ترتيب الاختيار الفعلي

يجب أن يطبق `ApiKeyScheduler` الخطوات التالية قبل كل طلب:

1. يرشح المفاتيح المفعلة التي يدعم Provider الخاص بها العملية أو النموذج المطلوب.
2. يستبعد المفاتيح الموجودة في `cooldown`، أو التي وصلت إلى حد التوازي، أو التي تجاوزت quota المسجلة محلياً.
3. يرتب المفاتيح حسب `priority` تصاعدياً، ثم يفضل المفتاح الأعلى صحة، ثم الأقل استخداماً داخل المستوى نفسه. هذا يمنع احتكار مفتاح واحد عند تساوي الأولوية.
4. يجرب المفتاح الأساسي مرة واحدة، ثم يسمح بإعادة محاولة قصيرة فقط للأخطاء المؤقتة. بعد ذلك ينتقل إلى المرشح التالي بدلاً من تكرار الطلب على مفتاح ميت.
5. إذا فشلت كل المفاتيح، يعيد خطأً موحداً يوضح أن AI غير متاح مؤقتاً، مع إبقاء التطبيق والألعاب والسبورة تعمل بدون AI.

يكون ترتيب Providers مستقلاً عن ترتيب المفاتيح. فلكل عملية AI يمكن تحديد `providerPriority` و`keyPriority`; وبذلك يمكن للمدرس أن يجعل Google-1 أولاً، ثم Google-2، ثم Groq-1، ثم OpenAI-1، أو يجعل Provider آخر أولوية أعلى دون إعادة إدخال الأسرار.

#### ج. تصنيف الفشل والـCircuit Breaker

لا يجوز تدوير المفاتيح عشوائياً عند كل خطأ؛ يجب تصنيف الاستجابة:

| الحالة | الإجراء |
|---|---|
| 401/403 أو مفتاح غير صالح | إيقاف المفتاح فوراً، وضعه `needs-check`، وعدم تجربته حتى اختبار يدوي ناجح. |
| 429 أو quota | وضع المفتاح في `cooldown` حسب `Retry-After`، أو مدة تصاعدية إن لم تصل المعلومة، ثم الانتقال للمفتاح التالي. |
| timeout أو انقطاع شبكة | إعادة محاولة واحدة قصيرة ثم تدوير المفتاح. |
| 408 أو 5xx | إعادة محاولة محدودة مع backoff ثم فتح الدائرة وتدوير المفتاح. |
| 400 بسبب payload أو schema | عدم تدوير كل المفاتيح؛ إصلاح الطلب وإرجاع خطأ validation واضح. |
| رفض محتوى أو policy error | عدم اعتبار المفتاح معطلاً؛ تسجيل الرفض للعملية فقط والعودة للمدرس. |

بعد عدد متتالٍ قابل للضبط من الأخطاء المؤقتة، يفتح النظام دائرة المفتاح ويضعه في `cooldown`. عند نجاح اختبار health-check أو انقضاء المدة يعود إلى `active` تدريجياً، مع منع عودته المفاجئة إلى ضغط كامل.

#### د. خوارزمية التدوير والـbackoff

```typescript
async function generateWithRotation(request: AiRequest) {
  const candidates = scheduler.getCandidates(request);
  const errors: RotationError[] = [];

  for (const key of candidates) {
    const lease = scheduler.acquire(key.id);
    if (!lease) continue;
    try {
      const provider = providerRegistry.for(key.provider);
      const response = await withTimeout(
        provider.generate(decrypt(key.encryptedSecret), request),
        request.timeoutMs ?? 30_000,
      );
      scheduler.markSuccess(key.id);
      return response;
    } catch (error) {
      const classified = classifyProviderError(error);
      errors.push({ keyId: key.id, provider: key.provider, ...classified });
      scheduler.markFailure(key.id, classified);
      if (classified.nonRetryablePayloadError) throw toSafeClientError(classified);
      await backoffIfNeeded(classified);
    } finally {
      scheduler.release(lease);
    }
  }

  throw new AiUnavailableError({ attempted: errors.length, retryAfterMs: scheduler.nextRetryAt() });
}
```

يجب دعم `requestId` و`idempotencyKey` لمنع تكرار توليد سؤال أو تقرير عند إعادة إرسال الطلب. ويجب أن يكون لكل طلب حد زمني، وحد أقصى لعدد المحاولات، وحد أقصى لحجم السياق.

#### هـ. واجهة إدارة المفاتيح

تُضاف في `SettingsPanel` أو لوحة AI شاشة إدارة واضحة للمدرس، تشمل إضافة مفتاح، اختيار Provider، اسم داخلي، أولوية رقمية أو سحب وإفلات، النماذج المسموح بها، تفعيل/تعطيل، اختبار الاتصال، وإعادة تفعيل المفتاح المتوقف. تعرض الشاشة الحالة الصحية، آخر استخدام، سبب آخر فشل، زمن التبريد، والاستهلاك التقريبي لكل مفتاح دون كشف السر.

يجب توفير وضعين: **ترتيب صارم** يلتزم بالأولوية تماماً، و**توزيع متوازن داخل نفس الأولوية** لتقليل استهلاك مفتاح واحد. يظل القرار للمدرس؛ لا يتم تفعيل Provider جديد أو استخدام مفتاح جديد دون إظهار حالته، ولا تُحذف المفاتيح القديمة تلقائياً.

#### و. Registry للمزودين

تنفذ Providers خلف واجهة موحدة:

```typescript
interface AiProviderAdapter {
  id: Provider;
  listModels(secret: string): Promise<string[]>;
  generate(secret: string, request: NormalizedAiRequest): Promise<NormalizedAiResponse>;

```

يجب أن يكون لكل Provider محول مستقل للـbase URL، headers، اسم النموذج، شكل الرسائل، حدود tokens، parsing، وhealth-check. لا يوضع `if/else` ضخم داخل route. ويجب أن تمر كل عمليات التحليل والتوليد والسبورة والتليبرومبتر عبر `aiClient` ثم route الخادم، لا عبر استدعاء مباشر من المتصفح.

#### ز. الأمان والخصوصية

تُشفّر المفاتيح بـAES-256-GCM مع key تشغيلي خارج قاعدة البيانات، ويُحظر حفظها في localStorage أو Zustand persist أو ملفات markdown أو تقارير الأعطال. تُنقى الأخطاء قبل إعادتها للواجهة، ويُمنع إرسال أسماء الطلاب أو إجاباتهم إلى Provider إلا بعد تفعيل المدرس لنطاق البيانات والموافقة على ذلك. يجب أن يدعم النظام حذف السر فعلياً، وتدوير مفتاح التشفير، ونسخ احتياطي لا يحتوي plaintext.

#### ح. الاختبارات المطلوبة لنظام التدوير

يجب اختبار الأولوية، التعادل، cooldown، 401، 429، timeout، 5xx، payload 400، فشل جميع المفاتيح، استعادة مفتاح بعد health-check، التوازي، idempotency، إعادة التشغيل، وانقطاع الشبكة. كما يجب اختبار أن AI إذا تعطل لا يعطل الشرائح أو السبورة أو الألعاب أو التقارير الأساسية.


(كما هو مفصل في البرومبت السابق).

# خطة التنفيذ المتكاملة والإلزامية — Bisalasa AI + Moodle + API Rotation

## 1. المبادئ غير القابلة للكسر

يظل التطبيق غرفة عمليات للمدرس عبر OBS/Zoom. الطلاب لا يدخلون بسلاسة، ولا ينفذ AI أو Moodle أو نظام العدالة قراراً تعليمياً نهائياً دون تحكم المدرس. أي اقتراح AI يُعرض كمسودة، وأي تدخل أو لعبة أو تقرير يمكن للمدرس تشغيله أو إلغاؤه. عند سقوط الإنترنت أو Moodle أو كل مفاتيح AI، يستمر المسار المحلي للشرائح والسبورة والألعاب والتقارير الأساسية.

## 2. مراحل التنفيذ

| المرحلة | النطاق | مخرجات القبول |
|---:|---|---|
| 0 | تثبيت العقود والجرد | خريطة الملفات، حالات الاستخدام، invariants، وخطة rollback. |
| 1 | طبقة الأسرار والإعدادات | تشفير، CRUD للمفاتيح، عدم كشفها للعميل، واختبار اتصال يدوي. |
| 2 | Provider Registry | محولات Google/Groq/OpenAI/Mistral، parsing موحد، وتصنيف أخطاء. |
| 3 | Scheduler والتدوير | أولوية، cooldown، circuit breaker، backoff، quota، concurrency، idempotency. |
| 4 | aiClient والعمليات المنظمة | تحليل الدرس، توليد الأسئلة، مساعدة السبورة، أدوات التليبرومبتر، وموافقة المدرس. |
| 5 | تكامل Moodle | إعدادات URL/token/course، ربط الطلاب، سحب الأسئلة والدرجات، وعزل فشل Moodle. |
| 6 | Live Sync | مزامنة خلفية قابلة للإيقاف، cursor/last-seen، deduplication، ومؤشر فهم لحظي. |
| 7 | نظام العدالة | `pickStudentByIdea`، سجل التدخل، انتهاء التدخل بعد إجابة صحيحة، وعودة العدالة العادية. |
| 8 | التقارير | تقرير حصة، تقرير طالب، تقدم المنهج، PDF عربي، وتحليل AI اختياري بعد الموافقة. |
| 9 | أدوات المدرس المتقدمة | المستمع الصامت اختياري، الإتقان التنبؤي، الاسترداد الذكي، والتنبيهات القابلة للإغلاق. |
| 10 | الاختبارات والإطلاق | اختبارات عقود، أمان، متصفح، فشل مزودين، 10,000 سيناريو، build، وحزمة تسليم. |

لا يبدأ Live Sync أو الميزات التنبؤية قبل ثبات طبقة المفاتيح والعقود الأساسية. ولا تُفعّل ميزات الصوت أو التحليل التلقائي افتراضياً.

## 3. عقود البيانات المقترحة

تُفصل بيانات الأسرار عن `AppSettings` كلما أمكن. إذا فرضت بنية المشروع التخزين في JSON، يحفظ JSON metadata فقط ويُحفظ السر في مخزن مشفر منفصل. يضاف لـMoodle سجل اتصال مستقل يحتوي URL وcourseId وtoken مشفراً وحالة الاتصال، ولا يُستخدم token Moodle في AI rotation.

تحتاج المزامنة إلى `syncCursor` لكل course/session، وسجل raw event hash لمنع التكرار، ووقت UTC بالميلي ثانية. كل حدث Moodle يجب أن يكون قابلاً لإعادة المعالجة بأمان، وكل تقرير يجب أن يحمل `sessionId` ونسخة البيانات التي بني عليها.

## 4. ترتيب التنفيذ العملي

يبدأ التنفيذ بتدقيق الكود الحالي والعقود الموجودة، ثم إنشاء اختبارات scheduler قبل ربط الواجهة. بعد ذلك تُبنى واجهة إدارة المفاتيح وتُختبر محلياً بمزود mock. ثم تُربط العمليات الموجودة دون تغيير فلسفة الموافقة. بعد نجاحها يُضاف Moodle في وضع قراءة فقط، ثم الربط اليدوي للطلاب، ثم polling قابل للإيقاف، ثم العدالة والتقارير. لا يُسمح بالكتابة إلى Moodle أو إنشاء اختبارات خارجية في المرحلة الأولى.

## 5. سياسة التشغيل والفشل

كل عملية خارجية لها timeout، retry budget، correlation ID، وsafe error. عند فشل Moodle يظهر للمدرس آخر وقت مزامنة وحالة stale مع زر إعادة المحاولة، ولا تختفي البيانات المحلية. عند فشل AI يظهر زر إعادة المحاولة واختيار Provider آخر، وتظل النتيجة اليدوية متاحة. عند انتهاء كل مفاتيح AI لا يُفتح loop لا نهائي ولا يتكرر الطلب تلقائياً بلا حد.

## 6. خطة الاختبار

تغطي الاختبارات unit وintegration وbrowser وfailure injection. تشمل مصفوفة المفاتيح: مفتاح واحد، مفاتيح بأولويات مختلفة، Provider مختلط، 401، 429 مع Retry-After، timeout، 5xx، جميعها متوقفة، عودة مفتاح، سباق طلبين، وإعادة تشغيل الخادم. وتشمل Moodle: token خاطئ، URL غير متاح، course فارغ، أسماء متشابهة، طالب غير مطابق، إجابة مكررة، إجابة متأخرة، وتوقف polling أثناء الحصة.

تُختبر كذلك invariants: عدم دخول الطلاب إلى بسلاسة، عدم عرض اقتراح AI دون موافقة، عدم إرسال سر للمتصفح، عدم تكرار النقاط، عدم اختيار طالب غائب، عدم سقوط الألعاب عند غياب Moodle، وعدم فقدان الشريحة الحالية. تُنفذ مصفوفة كبيرة من السيناريوهات، مع تسجيل النتائج والـseed والـrequestId لسهولة الإعادة.

## 7. معايير الإطلاق

لا تُعتبر الميزة مكتملة إلا إذا مر TypeScript وlint وbuild، ونجحت اختبارات API والعقود، واختبار المتصفح، واختبار PDF العربي، واختبارات الفشل، وفحص الأسرار، واختبار استعادة النسخ الاحتياطية. يجب تقديم سجل تغييرات، ملف إعدادات نموذجي بلا أسرار، دليل تشغيل، وطريقة تعطيل AI وMoodle فوراً.

## 8. ترتيب الأولويات المقترح للمنتج

الأولوية الأولى هي موثوقية local-first والتقارير والسبورة. الثانية هي API rotation وAI المنظم بموافقة المدرس. الثالثة هي Moodle read-only والمزامنة. الرابعة هي العدالة والتنبيهات. الخامسة هي الإتقان التنبؤي والمستمع الصامت وتقارير أولياء الأمور؛ هذه الميزات لا تُفعل افتراضياً قبل قياس أثرها وخصوصيتها.

# خطة التدقيق العميق لمنصة «بسلاسة»

**الهدف:** تحويل التدقيق من اختبار فتح النوافذ إلى اختبار حصة حقيقية يديرها مدرس أمام طلاب، بحيث تكون كل لعبة وأداة ولوحة مرتبطة بسياق الدرس والطلاب والجلسة، وتظل قرارات النقاط والاحتفال بيد المدرس.

## المبدأ الحاكم

> «بسلاسة» ليست مجموعة ألعاب مستقلة؛ إنها غرفة عمليات مدرس. اللعبة الناجحة هي التي تساعد المدرس على إدارة لحظة تعليمية من المنهج، وتُبقي الطالب مشاركاً دون أن تنتزع التحكم من المدرس.

## الأدوار التي سيحاكيها الاختبار

| الدور | ما الذي نختبره |
|---|---|
| المدرس أثناء الحصة | اختيار درس، فكرة، خطوة، طالب، لعبة، سؤال، إجابة، نقاط، احتفال، انتقال، إيقاف، استئناف، إنهاء الجلسة |
| الطالب | الظهور في الاختيار، الاستبعاد عند الغياب، المشاركة، الإجابة الصحيحة والخاطئة، التعادل، الترتيب، بطاقة الطالب |
| مدير البيانات | إنشاء/تعديل/حذف الصفوف والطلاب، الحضور، الجلسات، النسخ الاحتياطية، الاستيراد، الاستمرارية |
| المطور | عقود TypeScript، رسائل iframe، API dispatcher، التخزين، التزامن، إلغاء المؤقتات، cleanup، عدم وجود state updates أثناء render |
| المختبر | الحدود، النقر المكرر، إعادة التحميل، فقدان الدرس، فقدان الصف، وقت الصفر، إجابة فارغة، RTL، reduced motion، viewport ضيق |

## مراحل التنفيذ

### المرحلة A — جرد العقد

تحديد كل لعبة، كل لوحة، كل زر، كل شرط فتح، وكل مصدر بيانات. يتم وسم كل عنصر بـ: يحتاج درساً، يحتاج صفاً، يحتاج طلاباً، يحتاج جلسة، أو مستقل عن الحصة.

### المرحلة B — عقد المنهج والأسئلة

فحص كل manifest في `public/slides` وطبقة `question-provider`. يجب أن يمر السؤال إلى اللعبة مع مصدره: `lessonId`, `ideaId`, `stepNumber`, `text`, `correctAnswer`, `options`, `rewardPoints`, `difficulty`, و`gameReady`. لا تُنشأ أسئلة تجريبية خارج المنهج عند غياب الدرس.

### المرحلة C — نموذج الحصة الحية

يُعرّف الاختبار دورة حصة قابلة للتكرار:

`فتح التطبيق → اختيار/إنشاء صف → تحميل درس → بدء جلسة → اختيار فكرة → اختيار طالب → فتح لعبة منهج → سحب أسئلة الدرس → إجابة/timeout/skip → منح أو منع النقاط → احتفال اختياري → سؤال تالٍ → إنهاء اللعبة → تقرير الجلسة`.

كل انتقال يجب أن يكون قابلاً للإلغاء أو الاستئناف، وألا يترك `activeGame` أو timer أو listener أو طالباً مختاراً عالقاً بعد الإغلاق.

### المرحلة D — إصلاح الألعاب

تُراجع الألعاب التسع على أربع طبقات: setup، مصدر السؤال، دورة الجولة، النتيجة والتنظيف. تُمنع اللعبة من البدء إذا كانت متطلباتها غير متوفرة، وتعرض رسالة عملية للمدرس بدلاً من crash أو شاشة فارغة.

### المرحلة E — إصلاح اللوحات والخصائص

تُراجع الشاشات التي تفتحها الأشرطة الجانبية والسفلية: الصفوف، الطلاب، المجموعات، الإعدادات، الأصوات، الاحتفالات، التليبرومبتر، السبورة، AI، المتصدرين، كارت الطالب، التحدي الأسبوعي، الدرجات، والهدايا. كل زر يجب أن يملك حالة loading/empty/error/success، ومسار رجوع، وحماية مناسبة للعمليات الهدّامة.

### المرحلة F — التحقق الآلي والمتصفح

يُنشأ مولد حالات deterministic ينتج 10,000 سيناريو على الأقل من حاصل ضرب الأبعاد التالية:

| البعد | القيم النموذجية |
|---|---|
| حالة الدرس | بلا درس، درس flat، درس ideas، درس بلا أسئلة، سؤال واحد، أسئلة كثيرة |
| حالة الصف | بلا صف، صف فارغ، طالب واحد، عدة طلاب، تكرار أسماء، طالب غائب |
| الجلسة | بلا جلسة، نشطة، متوقفة، منتهية، مستعادة بعد reload |
| اللعبة | كل لعبة مدعومة، إعداد، لعب، timeout، نتيجة، إعادة تشغيل |
| السؤال | MCQ، نصي، إجابة صحيحة، خاطئة، فارغة، تكرار، بلا options |
| التفاعل | نقرة واحدة، نقرة مزدوجة، ضغط سريع، Escape، إغلاق، إعادة فتح |
| البيئة | RTL، portrait، landscape، zoom، reduced-motion، viewport ضيق |
| التزامن | تحميل متأخر، تغيير درس، تغيير صف، reload، API error، stale response |

بدلاً من الادعاء بأن 10,000 نقرة يدوية تعادل اختباراً شاملاً، ستُنفذ الحالات جميعاً عبر model/API/unit harness، بينما تُنفذ مسارات المتصفح الواقعية لكل خطورة عالية ولكل لعبة ولكل لوحة رئيسية. تُحفظ كل حالة ونتيجتها وسبب الفشل في سجل قابل للفرز.

## invariants إلزامية

1. لا تبدأ لعبة منهج بلا أسئلة صالحة من الدرس الحالي.
2. كل سؤال معروض ينتمي إلى `lessonId` الحالي، وإلى الفكرة الحالية عند اختيار current-idea.
3. لا تتضاعف النقاط بسبب نقر مزدوج أو تشغيل handler مرتين.
4. السؤال الذي انتهى بإجابة أو timeout أو skip يُعلّم كمستخدم وفق سياسة اللعبة.
5. لا يظل timer أو listener أو overlay نشطاً بعد إغلاق اللعبة.
6. الطالب الغائب لا يظهر في الاختيار العشوائي أو المشاركين الجدد إلا بإذن صريح.
7. لا يتغير سؤال الجولة بسبب إعادة render أو تغيير غير متعلق باللعبة.
8. إعادة تحميل المتصفح لا تنهي الجلسة النشطة تلقائياً.
9. إغلاق overlay أثناء اللعب يطلب تأكيداً ولا يفقد حالة الجلسة دون قرار المدرس.
10. كل عملية API الفاشلة تظهر للمدرس برسالة قابلة للفهم ولا تترك loading دائماً.
11. كل زر قابل للوصول بالكيبورد وله label أو title دال.
12. تفعيل reduced-motion لا يوقف الوظيفة، بل يزيل الحركة غير الضرورية فقط.
13. كل لعبة تعرض مصدر السؤال أو الفكرة/الخطوة للمدرس عندما تكون الأسئلة منهجية.
14. لا تُرسل بيانات الطلاب إلى AI إلا بعد تفعيل صريح، وبأقل سياق لازم.
15. كل نتيجة لعبة تُربط بالجلسة والطلاب المشاركين بطريقة قابلة للتقرير.

## بوابات النجاح

| البوابة | شرط المرور |
|---|---|
| logic | لا خروقات invariants في 10,000 حالة مولدة |
| curriculum | كل سؤال لعبة يتتبع إلى lesson/idea/step صالح |
| browser | مرور كل الألعاب واللوحات في مسارات مدرس واقعية |
| data | CRUD والاستمرارية والتراجع بعد الفشل بلا سجلات يتيمة غير مقصودة |
